# 搜索策略（中央优先 + 全场蛇形覆盖）

> 起因：赛规第 16 页的现场布置图（图7）显示 20 个救援目标**紧凑堆在场地正中**，
> 而原搜索算法是"在场地中央一小片区域里纯随机取点"——两者都没做对。
> 本文记录赛规依据、原算法的问题、新算法的推导与验证。
>
> 代码：`src/rescue_robot/decision/decision_engine.py`
> 验证：`tools/fix_verifiers/verify_search_coverage.py`（已并入 `run_all.py`）

## 2. 图7 的量化（像素级测量）

对图7 做 24×16 采样得到色图，复原出的排布是 **6 格 × 4 格**、每格 ≈ 一个目标：

```
列:    1    2    3    4    5    6
行1:   O    O    ▲    B    O    O
行2:   B    G    G    G    G    ▶
行3:   ◀    G    G    G    G    B
行4:   O    O    B    ▼    O    O
```

| 图元 | 数量 | 对应 | 体积/形状 |
|---|---|---|---|
| 绿 G | 8 | 普通物资 | 40mm 正方体 |
| 黑三角 ▲▶◀▼ | 4 | 核心物资 | 40mm **正三棱锥**（俯视即三角） |
| 橘 O | 4（各占 2 格） | 伤员 | 80×40×40 长方体 |
| 蓝 B | 4 | 危险目标 | 40mm 正方体 |
| | **= 20** | 初赛 16 救援 + 4 危险 | ✅ 与文字完全吻合 |

**尺寸**：格宽 ≈ 96px，图幅包围盒 579×385px ⇒ **6×4 格 ≈ 240×160mm**，
物体之间**紧挨着**（无间隙）。

> **结论：不能直接导航到 (1500,1500)。** 按图7 的摆法那是**一坨紧挨的物体**，
> 开过去等于从物体上碾过去，还会撞飞几个。中央那一段必须**留停顿距离**。

## 3. 原算法的问题

```python
def _get_explore_target(self, rx, ry):
    """生成探索目标：场地中央 + 随机偏移（排除安全区内的点）。"""
    for _ in range(6):
        cx = 1500 + random.randint(-600, 600)      # → [900, 2100]
        cy = 1500 + random.randint(-600, 600)      # → [900, 2100]
        cx = max(200, min(2800, cx))               # ← 永远不生效
        cy = max(200, min(2800, cy))               # ← 永远不生效
        if not self._is_in_any_safe_zone(cx, cy):
            return (cx, cy)
    return (1500.0, 1500.0)
```

| # | 问题 | 后果 |
|---|---|---|
| 1 | **纯随机、无记忆** | 反复走同一片区域，没有覆盖保证 |
| 2 | 随机范围实际只有 `[900,2100]²`（1200×1200，**占全场 16%**） | **外圈 900mm 的环带永远搜不到** |
| 3 | `clamp(200, 2800)` 永远不生效（随机范围根本没到边界） | 注释里说"修过 y>2200 搜不到"，**真凶还在** |
| 4 | 每 8 秒换一个点 | 走不到最优点就换，白白在路上 |

> 第 3 条是典型的"注释声称修了、代码其实没修"：
> 修的是 clamp 的**上界数值**，而 clamp 本身在这个取值范围内**根本不会触发**。

## 4. 关键几何推导（车道参数是怎么来的）

相机 `config.Camera`：`HEIGHT_MM=210`、`TILT_DEG=30`、`FOV_DEG=77`、`RES=(640,480)`。
检测门限 `detection.py: _min_contour_area = 200 px²`。

```
f = W / (2·tan(FOV/2)) = 640 / (2·tan(38.5°)) = 402.3 px
目标成像面积 ≈ (size·f/d)²  ≥ 200  ⇒  d ≤ 40·402.3/√200 = 1138 mm
```

即 **40mm 目标的可靠探测距离上限约 1138mm**（比"1.1m"好记）。

车道**单侧**可靠探测半宽 Δy 由两条约束联立（目标在机器人侧前方）：

```
① 在水平 FOV 内：  Δx > Δy / tan(38.5°) = 1.258·Δy
② 面积过门限：     Δx² + Δy² < 1138²
⇒ 2.583·Δy² < 1138²  ⇒  Δy < 708mm
```

**理论半宽 708mm**，工程上取 **500mm**（对应约 400px² = 2× 门限），
宁可多跑一条车道，也不要"扫过却没看见"。

### 车道取值

车道必须**同时**满足：

| 约束 | 取值 | 依据 |
|---|---|---|
| 距场心足够远（**别碾物体堆**） | ≥ 500mm | 物体堆半径 120mm + 车半对角线 212mm ⇒ 至少 332mm |
| 避开顶/底安全区（**进对方安全区直接结束本轮**） | y ∈ [550, 2450] | 安全区高 300 + 车半宽 150 + 余量 100 |
| 相邻车道间距 ≤ 2×500 | — | 否则中间有盲带 |

两条硬约束把车道**挤成上下两组**（场心 ±500 之外各铺一组），最终：

**车道 y = 550 / 1000 / 2000 / 2450**（间距 450 / 1000 / 450，关于场心对称）

**行进路径距场心最近 500mm** —— 正好压在禁入边界上，不会碰到中央物体堆。

## 5. 新算法

```
搜索计划 = [ 中央优先路点 ] + [ 全场蛇形车道上的路点 ]
```

| 段 | 内容 | 说明 |
|---|---|---|
| **中央优先** | 1 个路点：从**机器人当前一侧**朝场心靠近，停在 600mm 处 | 整段行进中相机始终朝着场心；600mm 处 40mm 物体成像约 719px²，看得清 |
| **全场蛇形** | 4 条车道，每条从 x=300 扫到 x=2700（蛇形反向，减少横穿） | 每 750mm 一个路点，便于"被目标打断后续扫" |
| **兜底** | 计划走完后在整个场地内随机取点 | 保证任何情况下都不"无处可去" |

### 运行时行为

| 机制 | 值 | 说明 |
|---|---|---|
| 路点消费 | 距路点 ≤ 250mm | 与 `_explore_target_stable` 的到达阈值**统一**（旧值 150 → 每个路点要干等 8s） |
| 路点超时 | 25s | 到不了就跳过，避免死磕 |
| 重新武装中央段 | 投放**被判无效**时 | 赛规第 18 页：无效目标会被**取出重放场地中央** → 值得再看一眼（只插 1 个点，不重置已扫车道） |

### 为什么不是"逆序"或"螺旋"

- 逆序/螺旋同样是"从一个点扫到另一个点"，**没有覆盖保证**；
- 蛇形车道是**可验证**的：可以直接断言"场地作业区每个网格点都能在某个位姿下被看到"
  （见第 6 节），而随机/螺旋只能概率性声称。

## 6. 验证

`tools/fix_verifiers/verify_search_coverage.py`（已并入 `run_all.py`，**15/15 通过**）

用**几何可见性模型**（FOV 圆锥 + 面积门限，参数取自 `config.py`/`detection.py`）
把 21 个路点离散成 98 个位姿，逐点判定：

| 检查 | 结果 |
|---|---|
| 作业区（离墙 ≥150mm）每 100mm 网格点都能被看到 | ✅ 零漏检 |
| 兜底随机点能覆盖到场地外圈 | ✅ x 301~2699（旧实现封顶 2100） |
| 行进路径不穿越场心禁入区 | ✅ 最近 500mm |
| 搜索路点不落在任何安全区 | ✅ |
| 图7 中央堆：第 1 个路点即可见 | ✅ 24/24 |
| 到达路点后会推进 | ✅ |
| 计划确定、有限、无重复 | ✅ 21 点 |

### 已知残余盲区（**如实记录**）

`x ∈ [800,900] × y ∈ [50,150]` 这约 **100×100mm** 的一小块紧贴**底边围栏**。

成因：底边车道（y=550）沿 +X 走，而该片区域需要机器人位于其**左侧**才能进 FOV，
但车道起点是 x=300，差一点点够不到；x=300 处的竖直转道又只覆盖更靠左的范围。

判断：**车体 300mm 宽，本来就没法贴到离围栏 150mm 以内作业**；
且计划走完后的随机兜底会继续在全场取点，仍有机会覆盖。
若现场发现目标真的会被放在那个位置，可把 `EXPLORE_LANE_EDGE_MM` 降到 500
并把 `EXPLORE_X_MARGIN_MM` 降到 250（代价：贴墙余量只剩 100mm）。

## 7. ⚠️ 仿真保真度缺口（**这条最重要**）

**集成仿真根本不走探索分支。** 实测（`seed=1`，9000 帧）：

| 指标 | 实测 |
|---|---|
| `_get_explore_target()` 调用次数 | **0** |
| `_explore_target_stable()` 调用次数 | **0** |
| "无目标可用"的帧数 | **7 / 9000（0.1%）** |

原因：`IntegratedSim._random_position()` 把 14 个目标**散布**在半径 600~1414mm 的
环带里（还**刻意排除**距场心 600mm 内），相机总能在某个方向看见一个 →
决策引擎永远有目标可选 → 探索降级几乎不触发。

**所以：规范仿真基线"仍是 80/80/80/85/80"对本改动毫无证明力** ——
它只说明我没弄坏非探索路径。真正的验证靠第 6 节那个专门的验证器。

而**真实比赛恰恰相反**：按图7 的摆法，20 个目标挤在正中 240×160mm 里，
从出发区（如 4 号区，距场心 1909mm）看过去**一个都看不见**（远超 1138mm 探测上限）
→ **必须探索**。也就是说探索路径在仿真里被完全绕过、在真实场景里却是关键路径。

> **待办（建议）**：给 `IntegratedSim` 增加一种"目标集中在场心"的布局模式，
> 让仿真也能覆盖"开局无目标 → 探索 → 发现"这条链路。
> 在此之前，**任何声称"搜索策略没问题"的结论都必须引用第 6 节的验证器**，
> 不能引用仿真基线。

## 9. 还没确认的事

**现场开赛时 20 个目标到底是"集中在正中"还是"散布全场"，尚未确认。**
本文按"两种假设都成立"设计，所以两种情况下都不会跑废；但**策略上仍有差别**：

- 若确实集中在正中 → 中央优先那 1 个路点就能发现，**省下整场扫场时间**；
- 若散布 → 蛇形车道保证覆盖，只是要跑完 ~11.6m（约 29s）。

现场确认后可以进一步优化（例如把车道数从 4 降到 2、把中央段去掉）。
