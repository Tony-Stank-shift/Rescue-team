### 1.3 最大丢分点（代码级证据）

**丢分点 ①（最大）**：`target_selector.select_targets_for_trip` 只要场上有伤员，
**无条件只返回"最近的一个伤员"**，普通物资/核心物资一律不参与本趟选择：

```python
# src/rescue_robot/decision/target_selector.py:209-214
if include_injured:
    injured = world_map.get_injured()
    if injured:
        nearest = min(injured, key=lambda t: self._distance(robot_position, t.position))
        return [nearest]              # ← 直接返回 1 个，永远轮不到"3 个核心一趟"
```

实测后果（直接调选择器，脚本 `/tmp/goalexp/expG_verify_bug.py`）：

- 场景：10 普通 + 5 核心（其中 3 个挤在相距 <300mm 的一簇）+ 5 伤员，机器人在红安全区。
- `select_targets_for_trip(...)` → **永远返回 1 个 INJURED**（剩余 180s / 120s / 30s / 10s 全部一样）。
- 把伤员临时移出候选后，同一函数立刻返回 **3 个核心**（20~44 分/趟）。

决赛 seed42 的完整悲剧（脚本 `expF_trips.py`，事件逐条）：

```
PICKUP #1004 普通物资 → DELIVER  (首趟，规则要求)
PICKUP #1016 伤员 → DELIVER
PICKUP #1019 伤员 → DELIVER
PICKUP #1018 伤员 → DELIVER
PICKUP #1017 伤员 → DELIVER
PICKUP #1015 伤员 → DELIVER      ← 180s 用尽，只送掉 1 普通 + 5 伤员
结果: score=80 投递=6 trips=6，10 个普通 + 5 个核心一个没动
```

每趟 28.8s（13.3s 去 + 13.3s 回 + 2.2s 套取/投放）。5 个伤员 = 144s，**一趟不落地全是单目标趟**。

**丢分点 ②**：跑不快。执行器实际平均线速度只有 **99~138 mm/s**，而设计限速是
`max_linear_speed=850.0`（`motion_control.py:121`）、`LocalPlanner` 也按 850 设计
（`path_planner.py:286`）。逐帧速度直方图（`/tmp/exp2_speed.py`，seed42）：

| 线速度区间 mm/s | 帧占比 |
|---|---|
| 0~10（原地转） | 11.1% |
| 10~50 | 1.9% |
| 50~150 | **55.3%** |
| 150~300 | 30.5% |
| 300~500 | 1.3% |
| 500~850 | **0.0%** |

根因（代码级）：
- 纯追踪固定看前 `lookahead_idx=2` 个航点，而 A* 航点间距 50mm（`path_planner.py:25`）
  → 预瞄距离恒 ~100mm；线速度又取 `0.8 × 预瞄点距离`（`motion_control.py:189`）
  → 巡航速度被卡在 ~80mm/s 量级，**这是速度上限的真正来源，不是 850mm/s**。
- 朝向误差 > 0.45rad 时 `linear *= (1.0 - angle_ratio) = 0`（`motion_control.py:188-191`）
  → 12.8% 的帧完全停转（只转不走），实测 11.1% 帧原地旋转。
- 到达容差 40mm（`motion_control.py:112`，"略大于网格分辨率"——50mm 网格说反了），
  配合 80mm 的路径裁剪（`navigation_pipeline.py:317`）→ 最后一段反复微调爬行。

**丢分点 ③**：没有"末段保分"逻辑。`TIME_PRESSURE_S=30.0` 只切换了一个策略状态名，
`select_best` 的 `time_factor` 提权远不足以改变选择结果；甚至剩余 **10 秒**时
`select_targets_for_trip` 仍然去挑 1784mm 外的伤员（§1.3 实测）。最后 12~15s 基本白跑。

## 2. 为什么不是满分：丢的 2 个目标与扣分点的代码级原因

### 2.1 丢的 2 个目标 = 2 个危险目标（浅蓝正方体），而且是**故意不送**

`integrated_sim._default_target_specs()`（`simulation/integrated_sim.py:203-208`）默认生成
`6 普通 + 3 核心 + 3 伤员 + 2 危险 = 14 个`，其中 12 个可得分、2 个**禁止转运**。

这 2 个目标被正确排除，两条独立的防线：

1. `TargetSelector.score_target`：`points <= 0 → score = -1.0`（`target_selector.py:82-84`），
   `select_best` 再过滤 `score > 0`（`target_selector.py:153`）→ 危险目标永远选不中。
   `select_targets_for_trip` 只从 `get_regular_supplies() / get_core_supplies() / get_injured()`
   取候选，危险目标根本不在候选集合里。
2. 即使有 bug 把危险目标塞进 `start_trip`，`LoadManager.can_load_batch` 第一句就是
   `DANGEROUS_TARGET → (False, violation)`（`load_manager.py:188-190`）。
   实测：`can_load_batch([R,D]) = (False, DANGEROUS_TARGET)`（`/tmp/goalexp/expJ_rules.py`）。

**结论：基线 105 分就是该局的满分**（6×5＋3×10＋3×15 = 105）。
`delivered=12/14` 里的分母 14 包含 2 个"不许碰"的目标，所以"12/14"看起来像没做完，
实际是"12/12 可达目标全部送达"。

### 2.2 基线里没有扣分点：`valid=12` 说明零扣分

`valid == delivered == 12`，意味着 `SafeZonePlacer.classify` 对 12 次投放全部返回
`is_valid=True`（物资进物资区、伤员进伤员区），既没有 `WRONG_*_IN_ZONE`（-10 分/个），
也没有 `OUTSIDE/ON_FENCE`（不计分）。`LoadManager.release_all(placement_ok=True)`
（`load_manager.py:256-262` 的扣分分支）从未触发。

**本质**：默认仿真局的 14 个目标全部落在场地中部、离安全区很近（行程仅 17.9~22.2km 总计），
且 6 普通+3 核心刚好能被 3 趟装完，**这一局太容易**，掩盖了真实配比下的策略缺陷。
换真实配比（8/4/4/4）立刻掉到 115~130 分（§1.2）——这才是"为什么不是满分"的真实答案：
**不是被扣分扣掉的，是 180 秒内送不完**。

## 3. 按收益排序的前 5 条改进项（含改前/改后对比实验）

实验口径：`git HEAD = 0e8a5ae` 导出到 `/tmp/headtree`（避免被正在进行的修复改动污染），
运行时替换 `TargetSelector.select_targets_for_trip`，其余代码不动；
5 个种子（42/1/7/2026/12345）× 两种配比。脚本：`/tmp/goalexp/expK.py`。

### 改进项 1（最高收益）：取消"伤员绝对优先"，改为按**价值密度**比较

- **现状**：`target_selector.py:209-214`，场上有伤员 → 只挑最近 1 个伤员，物资簇永不入选。
- **改法**：对两类候选各算"本趟预期收益 / 本趟预期耗时"，取密度高者：
  - 伤员单趟：`15 / (overhead + 2d/v)`；
  - 物资趟（普通+核心 ≤3 个）：`Σ分值 / (overhead + (d0 + 簇内跨度 + 300)/v)`；
  - `overhead≈9s`（套取 0.5+0.4s＋投放 0.4s＋对齐/转向余量），`v≈880mm/s` 实测等效速度。
- **改前/改后实测（平均分 / 平均送达可达目标）**：

| 配比 | 现状 | 密度策略 | 收益 |
|---|---|---|---|
| 初赛 8/4/4/4（可达16） | 121.0 / **12.2** | 121.0 / **14.2** | 多送 **2.0 个目标**（+16%） |
| 决赛 10/5/5（可达20） | 127.0 / **11.4** | 132.0 / **16.2** | 多送 **4.8 个目标**（+42%），平均 **+5 分** |

  逐种子看决赛：seed42 **80 → 120 分**（+40），seed1 150 → 130（-20），
  seed2026 135 → 145，seed12345 135 → 135。**最差种子从 40% 达成度抬到 60%**，
  平均分与送达数全面上升——这才是"拿最多分"的关键。
  （`overhead=9s` 与 `14s` 结果完全一致，说明该判据对参数不敏感，好实现。）
- **预期收益**：初赛实测 +16% 送达目标；决赛实测 +42% 送达、平均 +5 分，并消灭"5 个伤员跑满全场"的离散灾难。

### 改进项 2（第二收益）：把执行器平均速度从 ~138mm/s 拉到 300~400mm/s

- **现状**：`motion_control.py:206-219` 固定预瞄 2 个航点（≈100mm）＋ `motion_control.py:189`
  `linear = 0.8 × 预瞄距离` → 巡航 ~80mm/s；12.8% 帧因大转向角归零。
- **改法**：预瞄距离改为**按速度自适应**（如 `max(150, 0.35×v)`，或按时间 0.3~0.5s 折算），
  距离 PID 的 kp 提到能饱和到 850mm/s；大转角时允许**边走边转**（给 0.25 速度下限而不是直接归零）；
  终点段单独做制动门（接近最终航点时按距离限速），并把到达容差从 40mm 放宽到 80~120mm
  （与 80mm 裁剪阈值、`TransportPipeline` 的 150mm 套取范围对齐）。
- **预期收益**：直线段速度上限从 ~80mm/s 抬到 300mm/s 以上，理论可让"每趟 26.7s →
  12~15s"，在 180s 内从 7 趟抬到 10~12 趟 → 初赛 16 个可达目标有望全部送完。
  **本项未给出可信的改后数字**：我尝试的两版参考追踪器（kp=1.5~4、预瞄 150~350mm）
  都因"冲过目标点导致 ARRIVED 永不触发"而失败（实测 `score=0`，机器人持续以 848mm/s
  巡航 152km 不投递）。**说明这必须成套调参（预瞄+制动门+到达容差+重规划），不能只改一个数**，
  属于需要真机/长时间仿真的活，故不虚报收益。

### 改进项 3：末段时间保护（低风险、稳赚）

- **现状**：剩余时间只影响 `time_factor`（`target_selector.py:91-95`），不改变选谁；
  剩 10s 仍去 1.8m 外的伤员；一趟要 15~29s，最后 12~15s 的发车全是白跑。
- **改法**：`select_targets_for_trip` / `select_best` 加硬门限——剩余时间 < 预计单趟耗时
  （可用实测 15s 保守值）时，只允许选"当前位置已在安全区去向路径上、且不需要新增长途机动"的目标；
  或直接取消发车、进入安全区待命。`TransportPipeline` 相应不再启动注定超时的趟。
- **预期收益**：把最后 12~15s 的无效机动换成"不浪费上一趟的成果"；初赛实测可少 0~1 个目标白跑。

### 改进项 4：投放判定改用"目标落点"而不是车身中心坐标

- **现状**：`transport_pipeline.py:404-407` 用 `positions = [(rx, ry)] * n`（**机器人中心**）
  调 `SafeZonePlacer.classify_batch`。实测（`/tmp/goalexp/expJ_rules.py`）：

| 车中心位置 | 判定 |
|---|---|
| (1345,2820) 物资区中心 | valid=True |
| (1345,2600) 安全区外 60mm | valid=False, OUTSIDE |
| (1345,2645) 紫围栏外沿 | valid=False, OUTSIDE |
| (1205,2820) 贴左沿 | valid=False, ON_FENCE（边距 10mm 要求） |

  即"车在区外、目标被推进区内"这种**真机最常见**的成功投放，会被判 `OUTSIDE` → 不计分。
  这里的**降级方向是安全的**（不会误扣 10 分，因为 OUTSIDE 的 `penalty=0`），
  但会把成功记成失败，比赛成绩单上少分。
- **改法**：投放判定改成"目标落点"，来源按可靠性排序：① 投放后摄像头复核（安全区内/区外、
  物资区/伤员区）；② 车身坐标 + 朝向前推量（车身半长 + 推入距离）估算落点；
  ③ 保底：把"车中心已越过安全区外沿 ≥x mm"当作已投入（真机标定 x）。
- **预期收益**：消除"真机投进去了但软件不认"的漏记；对扣分无影响（当前只会低估、不会误扣）。

### 改进项 5：修掉 VIOLATION 死锁与多项稳健性缺口

- **现状**：`start_trip` 一旦判违规就 `_phase = VIOLATION`（`transport_pipeline.py:266`），
  而 `is_idle()` 只认 IDLE/COMPLETE → 即使后续 `start_trip` 能把相位改回 APPROACHING，
  整条链路已被打断；`integrated_sim` 没有任何 VIOLATION 恢复分支，真机一次误判就整场躺平。
- **改法**：违规判定后清空本趟目标、抬爪、把相位复位到 IDLE，并把该目标加入黑名单；
  上层对 `is_violation()` 给出恢复动作（而不是当无事发生）。
- **预期收益**：把"一次误判 = 整场 0 分"变成"这趟作废、下一趟继续"，是保命项。

## 5. 新发现的问题（含严重度）

### N-1【blocker】当前工作区集成链路整体回归：`integrated_sim` 满分变 0 分

- **现象**：`IntegratedSim` 每帧记录 `DECISION_ERROR`，5 种子全部 `score=0 / delivered=0 / trips=0`。
- **真实输出**：

```
seed=42 score=0 delivered=0 trips=0 DECISION_ERROR=8999
   ["DECISION_ERROR: cannot unpack non-iterable NoneType object"]
   ["DECISION_ERROR: local variable 'speed' referenced before assignment"]
```

- **根因（两处，第二处是当前的）**：
  1. `decision_engine.update` 把 `velocity` 默认成 `None` 后直接传给 `AnomalyHandler.check`
     （`decision_engine.py:187, 217-218`），而 `check` 里 `vx, vy = velocity`（`anomaly_handler.py:127`）
     → `TypeError`。仿真调用点没有传 `velocity`（`integrated_sim.py:278-284`）。
  2. 修 ① 之后新增：`speed` 只在 `if velocity is not None:` 分支里定义
     （`anomaly_handler.py:126-128`），却在分支外使用（`anomaly_handler.py:189`
     `if speed > 100 and dist < ...`）→ `velocity=None` 时 `NameError: speed`。
- **影响**：`integrated_sim` 是主回归基准，决策引擎每帧异常后只返回 `WAIT`，
  整台车"看起来在动（导航仍执行）但永远不投递"。**任何依赖集成仿真的验收现在都会得到 0 分**，
  极易被误判为"软件彻底不可用"。修复成本极低（`speed = 0.0` 兜底或整段用 `if velocity is not None` 包住）。
- **建议**：`check()` 内把 `speed` 初始化为 `0.0`，或把卡死检测也放进 `velocity is not None` 分支；
  同时给 `integrated_sim` 的 `DECISION_ERROR` 加"连续 N 帧即中止并报错"的硬失败，避免静默跑满 180s。

### N-2【high】投放判定用车身中心坐标（见改进项 4）

`transport_pipeline.py:404-407`。真机成功投放会被判 `OUTSIDE`（不计分）。已有证据见上。

### N-3【high】`VIOLATION` 相位无恢复路径（见改进项 5）

`transport_pipeline.py:266, 441-442`。一次误判 → 整场不再发车。

### N-4【medium】`time_remaining_s` 形同虚设

`target_selector.py:91-95, 199-206`。剩余 10s 仍选 1.8m 外目标，实测已证。

### N-5【medium】仿真默认配比与赛题不符，掩盖真实差距

`integrated_sim.py:203-208` 用 6/3/3/2，赛题初赛是 8/4/4/4（共 20）。
建议把默认配比改成赛题值（或让 `setup_match` 支持 `phase` 驱动），否则"105 分"会长期给出虚假安心。

### N-6【low】`_random_position` 回避场地中央 600mm 与"裁判重放点"耦合

`integrated_sim.py:239-243` 与 `decision_engine.py:314-326` 的 `_check_invalid_transport`
（目标距中心 <500mm 即视为"无效转运恢复"并重选目标）是同一现象的两次硬编码规避：

趟次被反复打断。建议把"裁判重放检测"改成带滞回/时间窗的一次性事件，而不是每帧扫全场。

## 6. 方法学说明：审计结论也可能是错的，必须独立复核

队长已用像素实测驳回了审计报告中的 **B2（安全区整体偏 300mm、紫围栏不该全包围、红区应贴顶边）**：
以 PDF 图7 的出发区四角反推场地边界，得 0.3473 px/mm；红内框实测 596×294mm、距场地上边 29mm、
中心 x = 795 ≈ 场地中心 794.5 → **与现有 `field_elements` 几何一致，无需修改**。

我把这一条作为**方法学案例**记录，理由有三：

1. 它证明"读代码得出的几何结论"必须用**外部基准（PDF 原图）** 交叉验证，
   否则会把"代码与我的理解不一致"误判成"代码错了"。
2. 我在本次推演中踩到过同类陷阱：一度把"105 分不是满分"当成软件缺陷，
   直到换了赛题真实配比才定位到真正的问题是**策略 + 速度**，而不是"少送了 2 个目标"
   （那 2 个恰恰是不该送的）。
3. 因此本文所有结论都附**可复现命令 + 真实输出**，凡未亲自跑通的一律标注"未验证"
   （如改进项 2 的提速收益），不猜测、不引用他人结论。
