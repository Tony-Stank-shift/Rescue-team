## 1. 问题清单（9 条）

### 【固件-1】IMU 初始化失败 → 整个 MCU 永久死循环，遥测一字节不发

| 项 | 内容 |
|---|---|
| **现象** | 串口能打开、`rx` 计数**自开机起恒为 0**，上位机表现为"串口故障/接线问题" |
| **证据** | 裸读 `/dev/ttyS1` 3 秒 0 字节；`/proc/tty/driver/serial` 显示 uart1 `rx:0`；换 `cat`/`pyserial` 都一样 |
| **根因** | 固件 `main()` 里 `if (MPU6050_Init(&hi2c2) != HAL_OK) Error_Handler();`，而 `Error_Handler()` 是 `__disable_irq(); while(1){}` **永久死循环**；**`Telemetry_Init()` 排在它后面** → 只要 IMU 没接好/上电时序不巧（`WHO_AM_I != 0x68`），固件就卡在初始化，遥测永远发不出来 |
| **为什么难查** | 电机、串口线、RDK 全是好的，故障点在最不相干的 IMU 支路上 |
| **修复** | 固件改为**降级运行**：`(void)MPU6050_Init(&hi2c2);`（失败不致命）。下游本来就做好守卫：`MPU6050_Update()` 有 `!initialized` 早退、`MPU6050_GetLatestSample()` 无效返回 false、遥测 IMU 行自动跳过 → 没有 IMU 时定位退化为纯里程计，但机器人不再变砖 |
| **状态** | ✅ 已烧录并验证（遥测恢复 84 行/秒） |

### 【固件-2】UART 接收静默死亡（TX 正常），最长静默 6 秒以上

| 项 | 内容 |
|---|---|
| **现象** | 遥测正常流动，但对 `PING`/`START`/`VEL`/`SERVO` **一律不回**（连 `ERR,FORMAT` 都没有），持续数秒后自行恢复 |
| **证据** | 6 轮"开关串口+PING"实测：3/6 轮首次无应答；**第 5 轮连续 3 次（≥6 秒）全部无应答**；而同一时刻下位机仍在发 84 行/秒遥测 |
| **根因** | STM32 HAL 在 ORE（溢出）处理里走 `UART_EndRxTransfer()`，会清掉 `CR1` 的 `RXNEIE/PEIE` 与 `CR3` 的 `EIE`。**`EIE` 一清，后续错误连 `HAL_UART_ErrorCallback` 都不再触发** → `RxState` 停在 `BUSY_RX` 且没有任何中断推动状态机 → 接收永久失效。**而 TX 完全不受影响，所以故障极难察觉** |
| **第一版修复为什么无效** | 我最初写成 `if (RxState != HAL_UART_STATE_BUSY_RX) { 重新武装 }` —— 而故障态**恰恰就是 `BUSY_RX`**，判断直接跳过 |
| **修复** | `Command_Update()` 内加 **RX 健康看门狗**：每 `RX_HEALTH_PERIOD_MS=500ms` **无条件**强制 ①拉回 `READY` ②清 `ErrorCode` 与 ORE ③`HAL_UART_Receive_IT` 重新武装。代价是极小概率丢 1 个在途字节（VEL 50Hz 丢 1 帧无影响，PING/START 有重试） |
| **效果** | 6 秒死窗口消失；最长连续失败从 3 次降到 2 次，每次 2 秒内自愈 |
| **状态** | ✅ 已烧录 |

### 【上位机-1】`START` 不清零里程计 → 累积位移被加到出发区位姿上

| 项 | 内容 |
|---|---|
| **现象** | 进 AUTONOMOUS 后 `A*: 起点 (3973, 2160) 不可通行`（场地只有 3000×3000，即场外约 1 米）→ 路径规划永远失败 → 车一动不动 |
| **证据** | 真机实测发 `START` 前后逐位对比：<br>`前: x=+0.6823 y=+1.0959 θ=-1.7043 enc=(921273,1240079)`<br>`后: x=+0.6823 y=+1.0959 θ=-1.7043 enc=(921273,1240079)`<br>**一模一样** —— 协议 §START 声称"清零局部里程计"，**实际并没有** |
| **根因** | `ChassisInterface.odom_to_upper()` 把 ODOM 当**相对位移**用（`x = _start_x + dx`），而 MCU 上电以来的累积量没被清 → 全部被当成"从出发区走的距离"加上去 |
| **算术复现** | 起点 (2850,2850)：`2850+1096=3946`、`2850-682=2168` ≈ 日志里的 `(3973,2160)` ✓ |
| **修复** | 新增 `set_odom_baseline()`：进 AUTONOMOUS 设起点时**主动记下当前 ODOM 当基线**，换算时先减掉。这样无论下位机清不清零、之前手动测试跑过多少，位姿都能正确归零 |
| **状态** | ✅ 已部署并真机验证 |

### 【上位机-2】旋转角用错参照系（本轮最隐蔽的一条）

| 项 | 内容 |
|---|---|
| **现象** | 位移**大小正确**（1557mm ≈ 1.5m）但**方向整体错**，位姿仍跑到场外 |
| **根因** | `odom_to_upper()` 用 `_start_theta`（**出发区**车头朝向）旋转，但 **ODOM 的 x 轴是「MCU 上电那一刻的车头方向」**。两者相差"从上电到把车摆好之间车被转过多少度"（实测 `θ_基线 = -97.7°`）→ 位移方向整体转错 |
| **修复** | 旋转角改为 `base_theta = θ0 − θ_基线`。**并验证 `θ_基线=0` 时与旧公式逐位一致**（正常情况零影响） |
| **状态** | ✅ 已部署 |

### 【上位机-3】`START_HEADING_DEG` 被 `AutonomousState` 覆盖（本轮修复过程中引入）

| 项 | 内容 |
|---|---|
| **现象** | 日志**自相矛盾**：`main` 打印起点 `+45°`，`autonomous_state` 却打印 `朝向=-90°` |
| **根因** | `main.py` 算好起点后，`autonomous_state.py:117` **又自己算了一遍** `get_start_pose(zone)`，**没带朝向参数** → 把用户设的 +45° 覆盖回默认 -90° |
| **教训** | 加新接口时**没有全局搜索"还有谁在算同一个东西"** |
| **修复** | 抽出公共函数 `field_elements.resolve_start_heading_deg()`，`main.py` 与 `AutonomousState` **统一调用**；已验证两处结果一致 |
| **状态** | ✅ 已部署（**下次开机第一件事是验证它**） |

### 【上位机-4】`start_match()` 一次失败就拒掉整场

| 项 | 内容 |
|---|---|
| **现象** | 进入 AUTONOMOUS 后立刻 `❌ 底盘 START 握手失败 → 拒绝进入自主模式 → 紧急停止` |
| **根因** | `start_match()` 里 PING / START 各只发**一次**、超时 **0.5s**、**不重试**。撞进【固件-2】的静默窗口就直接把整场比赛拒掉 |
| **关键认识** | 静默窗口期间下位机**根本没收到命令**，所以**单纯加长超时是无效的 —— 必须重发** |
| **修复** | 新增通用接口 `send_command_await()`：先 `drain_lines()` 排空残留行，再**重发 4 次 × 1.5s + 0.25s 间隔** |
| **实测验证** | `start_match` 连跑 3 次：**4ms / 3536ms / 5293ms 全部成功** —— 后两次在没有重试的旧代码下必然失败 |
| **状态** | ✅ 已部署并真机验证 |

### 【上位机-5】舵机 ACK 等待同样是"一次 + 0.5s + 不重试"

| 项 | 内容 |
|---|---|
| **现象（预判）** | 会导致"套取总是失败、反复抬爪后退"，**看起来像机构问题，实为通信问题** |
| **修复** | `SerialServoLift.lower()` / `raise_up()` 改用 `_servo_await()`（内部走 `send_command_await`） |
| **状态** | ✅ 已部署，**待真机验证** |

### 【上位机-6】一键启动事件只认一种 → 永久卡在 DEBUG

| 项 | 内容 |
|---|---|
| **现象** | 按 STM32 板上的启动开关**毫无反应**，永久停在 DEBUG |
| **根因** | 固件只在**边沿**发事件且分两种：下位机 `WAIT_START` 时发 `EVENT,START_BUTTON`；**已 `RUNNING` 时只发 `EVENT,BUTTON_LED_ON`**。而我们跑过手动测试让 MCU 变成 RUNNING → 上位机只认前者 → 永远等不到 |
| **修复** | 新增 `read_start_request()`，**两个事件都触发启动**（从操作员意图看，"把开关拨到 ON"就是"开始比赛"） |
| **状态** | ✅ 已部署并真机验证（日志出现 `收到一键启动请求: EVENT,BUTTON_LED_ON`） |
| **残余风险** | 若**开机时开关已经是 ON**，固件 `Command_Init` 里 `button_stable_pressed = button_raw_pressed` 直接取当前值 → 永不产生边沿 → 不发任何事件。**现场规避：开机前确认开关在 OFF** |

## 2. 新增功能：开场退避（进 AUTONOMOUS 后自动后退出场）

**需求**：现场小车**斜 45° 摆在出发区正方形的对角线上**（两差速轮靠近减速带、万向轮远离），
每次开赛都要先退一段才能进场地。做成开场动作后 → **按一次启动开关即可全自动**。

**实现**：`AutonomousState._run_startup_backup()`，在 `start_match()` 成功后、主循环开始前执行。

```yaml
# config/robot.default.yaml
match:
  startup_backup_mm_s: -300.0   # 负值=后退，0=关闭（默认关闭）
  startup_backup_s: 5.0         # 时长
```

**要点**：退避期间以 **50Hz** 持续发 `VEL`（下位机速度看门狗 300ms 保持 / 800ms 停车，发慢了会被判超时停车）；退避产生的位移由里程计自然记入，不需要额外修正。

**实测**：`🔄 开场退避：-300 mm/s × 5.0s → ✅ 开场退避完成（250 帧 VEL）` —— 车确实进了场地。

## 3. 新增配置：`START_HEADING_DEG`（现场声明真实车头朝向）

**为什么必须要有**：`odom_to_upper()` 拿"出发区车头朝向"旋转里程计位移，
**假设错多少度，整张地图就整体转错多少度**。而现场小车常常不是正朝场内摆的。

```bash
START_HEADING_DEG=45 ./run.sh        # 2 号区、车头朝出发区外侧角
```

**取值参考**（2 号区，起点 (2850,2850)）：

| 值 | 含义 |
|---|---|
| `-90°` | 车头正对场地内侧（-Y）—— **软件默认** |
| `-135°` | 车头朝场地中心 (1500,1500) 方向（对角线） |
| `+45°` | 车头朝出发区外侧角落 —— **此时"后退"才是朝场地中心** |

**本轮的实测反解**（用户确认车头朝外角 +45°）：

```
基线 ODOM: (0.686, 1.1093) m, θ=-1.7348 rad (-99.4°)
退避后 ODOM 增量: (+0.369, +1.513) m, 模长 1.557 m

START_HEADING_DEG=  -90.0°  →  位移 (  +117, +1553)  方向  +85.7°   ❌ 朝场外
START_HEADING_DEG= -135.0°  →  位移 ( +1181, +1015)  方向  +40.7°   ❌
START_HEADING_DEG=  +45.0°  →  位移 ( -1181, -1015)  方向 -139.3°   ✅ 朝场地中心（期望 -135°）
```

> **结论**：`+45°` 与期望方向（对角线朝场地中心 -135°）只差 `4.3°`，
> 那就是车在退避过程中慢慢偏掉的角度。**朝向判断被数据证实。**

## 4. 正确的启动流程（现场照做）

```bash
cd ~/rescue && TEAM_COLOR=red START_ZONE=2 START_HEADING_DEG=45 ./run.sh
```

1. 确认 **STM32 板上 `ON` 自锁开关在 OFF**
2. 启动程序 → 等 BOOT 自检通过 → 进 **DEBUG**（绿 LED 常亮）
3. **拨开关到 ON** → 进入 AUTONOMOUS
4. 日志要出现并**互相对得上**：
   ```
   main: 抽签出发区 = 2 号 → 起点 (2850.0, 2850.0, 0.785...)      ← +45°
   autonomous_state: 起点=(2850, 2850)mm，朝向=+45°                ← 必须也是 +45°
   里程计基线已记录: (...) m, θ=... rad
   底盘启动完成（PONG + ACK,START）
   🔄 开场退避：-300 mm/s × 5.0s
   ✅ 开场退避完成（250 帧 VEL）→ 转入自主导航
   ```
5. 退避后位姿应在 **(1669, 1835)** 附近，**不应出现 `A*: 起点 不可通行`**

**停车**：`Ctrl+C`。程序崩了也不怕——下位机速度看门狗 800ms 自动停。
（代码**刻意不用 `ESTOP`**：协议 §101 明确 `ESTOP` 锁板后 `START` 无法解锁，会逼着两场之间断电重启。）

## 7. 方法论：这一轮学到的三条

1. **"看起来像硬件" ≠ 硬件问题。** 本轮 7 条上位机问题里有 5 条症状都像"接线/硬件坏"
   （串口没收数、电机检测不到、按按钮没反应、车不动）。**先找"有没有自相矛盾的日志"**，
   比拆线快得多——本轮两次都是靠"同一量打出两个不同值"定位的。

2. **静默失败最贵。** 【固件-1】IMU 失败却打死整个 MCU、【上位机-1】START 不清零却无人报错，
   都属于"错得很安静"。**该 fail-fast 的地方 fail-fast，该降级的地方明确降级**，
   别让一个支路的故障静默地拖垮全局。

3. **加接口时要全局搜索同类计算点。** 【上位机-3】就是加 `START_HEADING_DEG` 时
   漏了 `AutonomousState` 里那次重复计算。**重复的"唯一来源"就不是唯一来源。**

### 部署方式确认

RDK 上 **不是 git 仓库**（`~/rescue/` 无 `.git`），是**纯 rsync 部署**。
即：**仓库是唯一事实来源**，RDK 只是运行副本。
→ 每次改完必须：`commit` → `push` → `rsync` 到 RDK，**顺序不能反**，
否则 RDK 上的临时改动会静默覆盖掉仓库内容（这次 `run.sh` 就差点是这种情况）。

> 同步核查建议固化成习惯：**动完现场就在两侧各跑一次 md5 清单 diff**。
> 这次正是"顺手全量比一下"才发现 `run.sh` 缺失的 ——
> 它不在任何一份"已知问题清单"里，因为**没人想过要去数文件**。

#### ② 构建 ↔ 芯片 ⏸ **受阻：SWD 链路不通**

想用 `STM32_Programmer_CLI -w <elf> -v -rst` 做字节级校验，但**连不上目标**。
已排除的全部软件侧可能：

| 排查项 | 证据 | 结论 |
|---|---|---|
| ST-Link 探针是否被 Windows 识别 | `Get-PnpDevice` → `5&1F94C9DB&0&6` **Status OK** | ✅ 正常 |
| 驱动是否正确 | Service=`WinUSB`，Provider=STMicroelectronics，**ProblemCode=0**，无 Upper/Lower filter | ✅ 正常 |
| 是否被进程占用 | `Get-Process` 无 `STM32/stlink/Cube/JLink/openocd` | ✅ 无占用 |
| 是否被 usbipd 劫持 | `usbipd list` → **Not shared**；WSL `lsusb` 看不到它 | ✅ 未劫持 |
| 探针固件是否活着 | `ST-LINK_gdbserver` **成功初始化探针**（不再报探针错） | ✅ 探针健康 |
| 目标 MCU 是否有电 | RDK 3 秒收到 **400 字节**遥测（ODOM/TEL 正常刷） | ✅ 有电在跑 |
| 固件是否禁用了 SWD | `stm32f1xx_hal_msp.c:79` 只有 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` = **只关 JTAG、保留 SWD** | ✅ 未禁用 |

试过并**全部失败**的组合：`mode` = 默认 / `UR`（复位下）/ `hotplug`；
频率含 `freq=100`；探针工具换用 `ST-LINK_gdbserver -m 0 / -m 1`。
一律报 `ST-LINK error (DEV_CONNECT_ERR)` /
`Failed to connect to device. Please check power and cabling to target.`

→ **探针好、目标有电、固件没禁用 SWD，但 SWD 信号到不了 MCU ⟹ 纯物理接线问题。**

**待查的物理清单**（按可能性排序）：
1. **SWD 排线是否真的插到板子的 SWD 座上**（不只是插了 ST-Link 的 USB 端）；
2. **GND 是否与机器人共地**（不共地则 SWD 必然失败，且现象与本次一致）；
3. **SWCLK / SWDIO 是否接反**（克隆探针的 4 脚丝印顺序与板子常不一致，这是经典坑）；
4. 探针的 **VTref / 3.3V 参考脚**是否接上（部分克隆探针要靠目标 3.3V 驱动电平转换）；
5. `mode=UR` 额外需要 **NRST** 接线——本次只接了 4 线的话 UR 必然失败，属正常。

> ⚠️ **不要用「能跑就行」放过这一项**：`-v` 是唯一能证明芯片里镜像与仓库一致的证据。
> 本次行为侧只提供了**旁证**（见下），不能替代字节级校验。

### 8.2 同步过程中的一次操作失误（留档，避免重犯）

本次同步时把命令写成 `rsync -az --delete docs rdk:~/rescue/docs/` ——
**源目录末尾漏了 `/`**。rsync 的语义是：

| 写法 | 含义 |
|---|---|
| `rsync -a SRC/ DST/` | 把 SRC 的**内容**同步进 DST ✅ 想要的效果 |
| `rsync -a SRC  DST/` | 把 SRC **这个目录本身**放进 DST → 变成 `DST/SRC/` ❌ 嵌套 |

结果：在 RDK 上生成了嵌套的 `~/rescue/docs/docs/`（内容其实是新的、md5 与本地一致），
而**顶层那份 `~/rescue/docs/` 没有被更新** —— 表现为"同步命令成功退出，但文件没变"。

**这次没造成损失**，但同一写法配上 `--delete` 是能真删文件的，属于高危操作。
已处置：删除嵌套目录、并用 `rsync -az --delete docs/ rdk:~/rescue/docs/`
（源带 `/`）重同步，md5 复核为 `bd4df190ae59` 两侧一致。

> **教训**：`rsync` 加了 `--delete` 之后，**源和目标两端的尾斜杠必须当成语法来读**，
> 不能靠"看起来对"。而且它**成功退出的退出码不能证明同步对了** ——
> 唯一可靠的验收还是回归到 **两侧 md5 清单 diff**（正是本节开头那个方法）。
> 这也是为什么本节坚持"全量比对"而不是"看 rsync 有没有报错"。
