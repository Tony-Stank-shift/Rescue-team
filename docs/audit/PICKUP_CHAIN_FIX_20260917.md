# 套取链修复（2026-09-17 真机 · 4 号区）

> **现场症状**（用户报告，日志 `09:12:28–09:14:49`）：
> ① 「识别到物体却不去套，反而移动一段距离，之后物体就不在视野里了」
> ② 「物体堆卡在车下」
> ③ 「一进 AUTONOMOUS 就报 `NO_ACTION_15S → EMERGENCY_STOP`」
>
> 本文记录**根因**、修复与验证。**结论：①③ 是软件缺陷；② 一半是软件缺陷、
> 一半是赛规图7 那种"物体紧挨成堆"的摆法本身导致的。**

---

## 1. 先说不是什么

排查中我一度怀疑**相机倾角标定**（`TILT_DEG=30°`）—— 因为地平面测距对它极敏感
（真实倾角与假定值差 2° → 1m 处距离误差就 ±15~21%）。**但这条不成立**：
30° 是现场声明的安装角，我没有任何测量数据能说明它错了，不该拿"敏感性"当嫌疑。

也一度怀疑**朝向换算符号**（`odom_to_upper` 的 `base_theta`）。**去核对了固件源码，
符号自洽**：`delta_theta = (right − left) / track_width`，右轮走得多为正 = 左转，
与 x 前 / y 左的右手系一致；上层旋转也与之匹配。**这条也不成立。**

**教训**：这两条都是"从敏感性/直觉推出来的嫌疑"，不是证据。日志里
`cmd v=0mm/s` 却能触发"已下发速度但无位移"告警，这个**自相矛盾**才是真线索 ——
它说明**有角速度、没有线速度**。

---

## 2. 根因：三条缺陷串成一条链

### 缺陷 A —— 车头偏差 >25.8° 时前进速度被压成 0（`motion_control.py:221`）

```python
angle_ratio = min(1.0, abs(angle_error) / (ANGLE_TOLERANCE_RAD * 3))  # 0.15×3 = 0.45rad
linear *= (1.0 - angle_ratio)      # ← 偏差 ≥25.8° 时 linear 恒为 0
```

车只原地转、位置不变。这就解释了日志里反复的 `cmd v=0mm/s`。

### 缺陷 B —— 近距"对准"数学上收敛不了 ⇒ **最后 10cm 永远进不去**

40~150mm 这段原本也要求"先对准再前进"。但近距时方位角极不稳定：

```
方位角误差 ≈ atan(目标位置抖动 / 距离)
抖动 50mm、距离 100mm → 27° > 25.8° 阈值 ⇒ linear 恒为 0
```

**而套住物体恰恰必须走完这 10cm。** 日志佐证：目标 `(1527,1522)` 从
**09:13:06 挂到 09:14:33（87 秒）**，车始终在 (1520,1520) 附近 ±100mm 打转：

| 时刻 | 车位置 | 距目标 |
|---|---|---|
| 09:13:20 | (1565,1524) | 38mm |
| 09:13:40 | (1511,1687) | 165mm |
| 09:14:05 | (1538,1488) | 36mm |
| 09:14:30 | (1564,1533) | 38mm |

### 缺陷 C —— 看门狗只按**位置**判"在不在动" ⇒ 10 秒后抢走导航目标

`autonomous_state.py` 原判据只有 `step_mm`（位置差）。**原地转向位置一点不变**，
于是"正在按指令对准"被判成"卡死"，10s 后 `navigation.explore()` 把导航目标
换成场地里一个随机点 → 车被支使去别处 → **物体出视野**（症状①）。

日志就是这个循环：

```
09:13:02 探索模式: target=(1959,1546)
09:13:20 探索模式: target=(2077,1977)
09:13:40 探索模式: target=(1769,761)
09:14:05 探索模式: target=(2287,1571)
09:14:29 探索模式: target=(783,1250)
```

### 缺陷 D —— "到位"判在**车心**上 ⇒ 整车压过物体（症状②）

夹爪 V2 是向下罩的框，**开口中心在车心前方 `DROP_FORWARD_MM=70mm`**、半深 50
⇒ 物体必须落在车心前方 **[20,120]mm** 才真在开口里。
而旧实现把"到位"判成"车心距物体 <40mm"——**车心压到物体时才算到位**，
此时物体早已落在开口**后方** 70mm。这就是"物体堆卡在车下"。

> ⚠️ **顺带查出一处"文档声称已实现、代码里根本没有"**：
> `SLEEVE_OPENING_MM` **从未被任何逻辑引用**。配置与注释都写着
> "捕获判据**必须**用它 / 现已按矩形开口复核"，但全仓库只有圆形
> `CAPTURE_RADIUS_MM`，矩形复核从来没写。（同类问题：搜索那边的
> `clamp(200,2800)` 也是"注释说修了、实际没生效"。）

### 缺陷 E —— 开局误报急停（症状③）

`StartMatch` 复位了 19 个量，**唯独没复位空闲计时器**，而它是在 `__init__`
（= 程序启动）那一刻起的：

```
09:12:28 程序启动（计时器起）
09:12:41~46 开场退避，车真的走了 1.5m（但决策引擎不知道，不是它发的指令）
09:12:47 进 AUTONOMOUS → idle = 18.4s → NO_ACTION_15S → EMERGENCY_STOP
```

## 3. 修复

| # | 文件 | 改动 |
|---|---|---|
| 1 | `motion_control.py` | 角度误差 ≤ **90°** 时保留前进速度下限（**弧线**靠近）；只有 >90° 才原地转正。新增"近距爬行段"（<150mm 不再要求对准，带角度阻尼慢速靠近） |
| 2 | `autonomous_state.py` | 看门狗**把转动也算"在动"**（窗口内累计转角 ≥30° = 在动）。位置判据保留 |
| 3 | `config.py` | **真正实现**矩形开口判据：`Placement.object_in_sleeve()`（前后 ∈[20,120]、\|横向\|≤75）与触发闸门 `should_stop_for_capture()` |
| 4 | `decision_engine.py` / `transport_pipeline.py` | 到位判据改用**套取框**（车心+L·朝向），不再用车心圆 |
| 5 | `decision_engine.py` | `start_match()` 复位 `_last_action_time` 与异常处理器计时 |
| 6 | `autonomous_state.py` | `_last_cmd` 保留真实角速度（原来写死 `0.0`，导致卡死告警漏报）；新增 **2Hz 诊断日志** |

### 新增诊断日志（下次现场直接用）

```
📊 pose=(1520,1520) θ=-45° | cmd v=0mm/s w=+0.85rad/s | 目标=(1527,1522) | nav=MOVING | 转运=APPROACHING
```

**为什么要打这两列**：真机出问题时原来的日志只有"是否在动"和一句 `cmd v=…`，
看不到 θ 与角速度 → **无法区分"在原地转"（linear=0/angular≠0）和"真的没动"**
（两者都 0）。这两种的处置**完全相反**，缺了这两列只能靠猜 —— 这次就是这么绕了弯路。

## 4. ⚠️ 我走过的一条弯路（留档，很重要）

修缺陷 D 时我第一版的做法是**把导航目标往前挪 70mm**：

```
导航目标 = 物体坐标 − 70 × 单位向量(车 → 物体)
```

**这个设计是错的**：它是**每帧随车位置重算的移动设定点**。实测车在追一个
后退的目标——目标从 `(721,2246)` 缓慢爬到 `(724,2249)`，永远到不了：

> **集成仿真 5 个种子从 80/80/80/85/80 直接掉到 0/0/0/0/0。**

正确做法是**让导航目标保持物体本身**（静止、稳定），把"到位"的判据从
**车心**换成**套取框中心**。改完之后仿真不但恢复，还**提升**了（见 §5）。

**教训**：给导航喂"依赖当前位姿的设定点"= 喂一个会跑的目标。
**而这次是仿真基线把它抓住的** —— 如果当时只看真机日志、或者嫌跑仿真慢而跳过，
这个 0 分会直接烧掉一整天现场。

## 6. 还没解决的 / 待观察

1. **物体紧挨成堆是物理难题，不是纯软件问题。** 按赛规图7，20 个目标挤在
   ~240×160mm 内、边贴边。车要套住其中任一个，都必须靠近到与相邻物体干涉的距离。
   本次修复能保证**不再整车压上去**（停在物体后方 70mm、由框去罩），
   但"贴着邻居套取而不碰倒它们"只能靠现场实测调 `DROP_FORWARD_MM` 与接近姿态。
2. **"与对方接触"反复误报**：日志里距离 143~340mm 反复触发/结束。
   用户判断是"物体堆卡在车下"造成的误检 —— 修复后物体不再被压到车底，
   应大幅减少；**但这条要现场复测确认**，若仍误报需单独查
   `opponent_tracker` 的目标筛选。
3. **`cmd v=284mm/s` 但 10 秒无位移**（09:14:30）—— 这次是**真的**打滑/堵转，
   很可能就是骑在物体上。修复后应消失；若再现，按"打滑/堵转"方向查。
4. **`TILT_DEG` 仍未实测**（`RUNBOOK §5.3` 第 1 项）。本次**没有**把它当嫌疑，
   但它的敏感性是真的（差 2° → 1m 处 15~21% 误差），标定一次只需 5 分钟。
